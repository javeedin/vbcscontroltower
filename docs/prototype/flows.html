Control Tower — Process Flows

The core journeys the product orchestrates — from feeding an FDD and having the AI build the app, through readiness, deployment and keeping monitoring live. Sample/conceptual flows.

1 · End-to-end lifecycle

Every product travels this loop; Control Tower has a screen for each stage.

flowchart LR
  I["💡 Idea"] -->|score & accept| R["📋 Requirements"]
  R --> D["🎨 Design"]
  D --> B["🔨 Build"]
  B --> T["✅ Test"]
  T --> Rel["🚀 Release"]
  Rel --> Op["📈 Operate"]
  Op -->|feedback / new idea| I

2 · FDD → components AI interpreter

Feed an FDD; the AI extracts a Blueprint you review, then templates + AI generate the VBCS app, which is validated before it's applied — and auto-registered for monitoring.

flowchart TD
  F["Feed FDD text"] --> X["AI extracts a structured Blueprint"]
  X --> R{"Human reviews & edits Blueprint"}
  R -- approve --> G["Generate VBCS artifacts: templates + AI"]
  G --> V["Validate: binding rules + schema"]
  V -- issues --> R
  V -- clean --> A{"Apply"}
  A --> Git["Commit to repo / VB Studio"]
  A --> Arc["or export import archive"]
  Git --> Reg["Auto-register as a Product"]
  Reg --> Mon["Monitored through to release"]

3 · AI builder pipeline sequence

Who calls whom. Two mandatory human gates (Blueprint, pre-Apply); the LLM runs outside VBCS via a Service Connection.

sequenceDiagram
  participant U as You
  participant CT as Control Tower
  participant LLM as LLM
  participant GEN as Generator
  participant VAL as Validator
  participant GIT as Repo / VB Studio
  U->>CT: Ingest FDD
  CT->>LLM: extract Blueprint (JSON)
  LLM-->>CT: Blueprint
  CT->>U: review Blueprint (edit)
  U->>CT: approve
  CT->>GEN: render artifacts
  GEN->>LLM: fill bindings / copy
  GEN-->>CT: BO + pages + flows + chains
  CT->>VAL: check rules + schema
  VAL-->>CT: findings
  CT->>U: review, then apply
  CT->>GIT: commit / import
  CT->>CT: auto-register product

4 · Release readiness (gate evaluation)

The signature monitor flow: gates sync from GitHub/Jira, a weighted score decides go/no-go.

flowchart TD
  S["Open release"] --> Sync["Sync gates: GitHub + Jira"]
  Sync --> G1["Tests green?"]
  Sync --> G2["Acceptance criteria present?"]
  Sync --> G3["Changelog + version bumped?"]
  Sync --> G5["Deployed to Test?"]
  Sync --> G6["No open blockers?"]
  G1 & G2 & G3 & G5 & G6 --> Calc["Weighted score"]
  Calc --> D{">= threshold & no blocking fail?"}
  D -- Yes --> Rdy["🟢 Ready to release"]
  D -- No --> Blk["🔴 Blocked / 🟡 warnings"]

5 · Data sync (how monitoring stays live)

Incremental, cached, idempotent — so pages are fast and API rate limits are respected.

sequenceDiagram
  participant T as Trigger (on-open / Sync now / cron)
  participant AC as Action Chain
  participant SC as Service Connection
  participant EX as GitHub / Jira / VB Studio
  participant BO as Business Objects
  T->>AC: run sync
  AC->>SC: GET changes since lastSync
  SC->>EX: REST call
  EX-->>SC: data
  SC-->>AC: mapped payload
  AC->>BO: upsert records
  AC->>BO: write activity log
  AC->>BO: set lastSync = now
  AC-->>T: counts + errors

6 · Deployment & rollback

Non-prod first (mirrors how Oracle updates Fusion pods), with a rollback path.

flowchart LR
  Dev["Dev"] -->|build passes| Test["Test"]
  Test -->|UAT + readiness OK| Prod["Prod"]
  Prod -->|if broken| RB["Roll back to previous version"]
  RB --> Prod

Two human checkpoints guard the AI builder (approve the Blueprint, approve before Apply), and nothing deploys to production automatically. The generator uses templates for VBCS metadata and the LLM for interpretation, so output obeys VBCS binding rules.
